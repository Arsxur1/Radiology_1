# Технический файл (проект) для государственной регистрации медицинского изделия

**Проект для регуляторного консультанта и юриста.** Основание — Постановление Кабинета
Министров РУз № 738 от 24.11.2025 (в силе с 26.02.2026), регистрирующий орган — Центр
безопасности фармацевтической продукции при Минздраве (uzpharm-control.uz). Требования к
составу документов взяты из вторичных источников (`ISTOCHNIKI-I-PRAVO.md`); перечень и
формы — сверить с текстом постановления. Места, требующие решения, отмечены **«Решить»**.

Редакция от 2 октября 2026 г. Версия ПО — ветка `claude/advanced-medical-imaging-product-tx6qyp`;
номер версии для регистрации — **Решить** (фиксируется перед подачей).

## 1. Описание изделия

**Наименование (рабочее):** medviz — программная платформа поддержки врача-рентгенолога.

**Вид:** программное обеспечение как медицинское изделие (SaMD), устанавливается на сервер
медицинской организации; доступ сотрудников — через браузер в сети организации.

**Функции** (ТЗ, требования FR; соответствие коду — `TRACEABILITY.md`):

| Функция | Требование |
|---|---|
| Приём исследований из PACS, обезличивание, связывание пациента, отправка заключения обратно в PACS | FR-1, SR-9 |
| Просмотр (MPR, оконные пресеты, сравнение) | FR-2 |
| Сегментация структур КТ/МРТ, объёмы, правки врачом | FR-3, FR-6 |
| Совмещение модальностей с проверкой врачом | FR-4 |
| 3D-модели подтверждённых структур | FR-5 |
| Сравнение во времени (без ИИ) | FR-7 |
| Находки-черновики на рентгенограммах ОГК, черновик заключения из подтверждённых находок | FR-8, SR-1 |
| Обучение и калибровка моделей на данных площадки под контролем (PCCP) | FR-9, FR-10, FR-11 |
| Роли, журнал аудита | FR-12, SR-8 |

**Принцип:** система **не ставит диагноз** и не принимает решений: она предлагает находки,
измерения и черновик; в заключение попадает только то, что врач подтвердил активным
действием (SR-1, SR-2). Заключение маркирует участие ИИ (закон ЗРУ-1115).

## 2. Назначение и условия применения

- **Назначение:** помощь врачу-рентгенологу в анализе рентгенограмм органов грудной клетки,
  КТ и МРТ: предварительные находки и измерения для проверки врачом, сравнение с прошлыми
  исследованиями, подготовка заключения.
- **Пользователи:** врачи-рентгенологи (решения по находкам), клиницисты (просмотр,
  подписанные заключения), администраторы, аудиторы.
- **Пациенты:** первая площадка — детский центр (NCMC, 0–18 лет). Каждая модель имеет
  явные границы применимости (модальность, область, возраст, толщина среза, аппараты);
  вне границ система **отказывает**, а не выдаёт результат с пониженной уверенностью (SR-7).
- **Не применяется:** для самостоятельной постановки диагноза; без врача; для УЗИ (не
  входит в первую версию); в режимах, где врач не может проверить результат.
- **Режимы:** RESEARCH (разработка, маркировка «не для клинического применения»), SHADOW
  (модели работают, врач их не видит — накопление свидетельств), ASSIST (врач видит
  черновики). Переход в ASSIST — только через гейт (п. 6).

## 3. Класс риска

**Предложение: класс IIa** (по аналогии с правилом 11 MDR ЕС, которое используется в
сходных системах классификации): ПО предоставляет информацию для принятия диагностических
решений; решение принимает врач, каждая находка проверяется, вне границ — отказ.

Доводы за возможный **IIb** (оценить консультанту): педиатрическая популяция; пропущенная
находка может задержать лечение. Меры, снижающие риск: обязательная проверка врачом,
режим SHADOW до доказательств, контроль дрейфа, мгновенный откат.

**Решить:** класс по классификатору РУз (с консультантом); путь регистрации — полный или
упрощённый (упрощённый — при одобрении FDA/CE/PMDA/MFDS/MHRA, которого нет).

## 4. Архитектура (кратко; подробно — `ARCHITECTURE.md`, `OBZOR-SISTEMY.md`)

- Два контура данных: **доверенный** (обезличенные снимки, находки, решения, аудит) и
  **идентифицирующий** (ФИО, номер карты — отдельная БД, раскрытие по цели с аудитом).
- Приём DICOM → обезличивание (псевдонимы HMAC с ключом площадки) → хранилище снимков и
  обезличенный просмотрщик (OHIF) → анализ в фоне (воркеры) → решения врача → заключение
  (печать, DICOM SR в PACS).
- Отказ компонентов ИИ не мешает просмотру (SR-4); состояние компонентов — «Состояние
  системы», `/ready`.
- Развёртывание: Docker Compose на сервере организации; HTTPS-шлюз; внутренние порты не
  открыты наружу; учётные записи — Keycloak.

## 6. Изменения моделей после регистрации (PCCP)

Предусмотренный план изменений (FR-10): новая версия модели регистрируется кандидатом в
**SHADOW** (врач не видит), набирает свидетельства на данных площадки (замороженный тест,
доля расхождений с подписанными заключениями, срезы по аппаратам и возрастам, происхождение
данных), проходит **гейт**, продвигается ответственным лицом с письменным обоснованием (в
аудит), откатывается мгновенно. Автообновление в ASSIST технически запрещено (SR-3).

**Пострегистрационный надзор:** журнал инцидентов в продукте (п. 5) — каждое сообщение
связано с версией модели; вывод разбора и смена статуса — в аудит; сводка по видам — в
отчёте пилота (агрегаты, без текста описаний). **Решить:** сроки уведомления регулятора о
серьёзных инцидентах по постановлению № 738.

**Решить:** допускает ли регуляторная практика РУз такой план изменений без повторной
регистрации каждой версии модели (как PCCP у FDA); если нет — какие изменения считаются
существенными.

## 7. Верификация и валидация ПО

**Верификация (выполнена, повторяется при каждом изменении):**
- автоматические тесты backend: 335 (57 модулей), включая проверку, что ссылки этого файла, файла рисков и трассируемости на тесты и документы существуют, включая сквозной путь, критерии приёмки
  раздела 10 ТЗ, сетевой путь PACS против настоящих DICOM-узлов, миграции на PostgreSQL
  (подъём, полный откат, повторный подъём);
- CI на каждое изменение: тесты, линтер, строгая сборка интерфейса, сборка образов,
  проверка шлюза в режимах HTTP/HTTPS, **проверка известных уязвимостей зависимостей**;
- живые проверки на стенде с настоящими компонентами (PACS в роли H-PACS, Keycloak, OHIF,
  HTTPS, резервное копирование и восстановление, нагрузка «год работы»: 60 000 исследований)
  — каждая записана с результатами в `ZHURNAL-RABOT.md`;
- матрица трассируемости требований → код → тесты: `TRACEABILITY.md` (21 требование).

**Клиническая валидация — не выполнена (главный пробел):**
- внешняя проверка рентген-модели на открытых детских наборах (`VALIDATSIYA-DETI.md`):
  на втором наборе (HWCMC, 0–14 лет) открытые модели различают норму и пневмонию слабо
  (AUROC 0,64–0,66); пороги не переносятся между больницами. **Поэтому клиническое
  применение (ASSIST) без валидации на данных NCMC не предлагается**;
- план: теневой прогон в NCMC 8–12 недель (`PILOT-NCMC.md`), калибровка и дообучение на
  данных площадки, замороженный тест площадки, затем решение о ASSIST по свидетельствам.
- **Решить:** дизайн клинической оценки для регистрации (ретроспективная на данных NCMC,
  проспективная в режиме SHADOW), этическое одобрение, число случаев.
