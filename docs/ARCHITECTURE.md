# Архитектура

Документ описывает архитектуру этапа 1 и заделы под последующие этапы. Соответствует
разделу 4 ТЗ. Принцип «не изобретать основание»: перечисленные компоненты используются
как есть.

## 1. Контуры (границы доверия)

```
                    ГРАНИЦА ВХОДА / ОБЕЗЛИЧИВАНИЯ (SR-9)
                                  │
   ┌───────────────────┐         │        ┌────────────────────────────────────┐
   │  Идентифицирующий  │         │        │        Доверенный контур           │
   │       контур       │         │        │      (обезличенные данные)         │
   │                    │         │        │                                    │
   │  Модальности ──C-STORE──►  Orthanc ──► Обезличивание ──► Orthanc (clean)   │
   │  Сетевая папка ────────►  (raw)         │  де-ид        │  MinIO (объекты)  │
   │                    │         │          ▼               │  PostgreSQL       │
   │  Таблица сопоставления       │     pseudo-map           │  Backend API      │
   │  «ID ↔ UUID» (защищ. БД) ◄───┘     (защищ. хранилище)   │  Celery/Redis     │
   └───────────────────┘                                     └────────────────────┘
```

- **Идентифицирующий контур** — единственное место, где есть связь «обезличенный UUID ↔ реальный пациент».
  Таблица сопоставления хранится отдельно, доступ строго ограничен (см. `docs/DATA-MODEL.md`, `patient_pseudonym_map`).
- **Доверенный контур** — всё остальное работает только с обезличенными данными.

## 2. Поток приёма (FR-1)

1. Модальность отправляет исследование по **C-STORE** на Orthanc (raw-узел) либо файлы падают в **сетевую папку** (резервный путь для аппаратов без Storage SCU).
2. Orthanc уведомляет backend (через `OnStoredInstance` / polling changes API).
3. **Сервис обезличивания** (`app/services/anonymization.py`):
   - генерирует/находит псевдоним пациента (UUID),
   - сохраняет соответствие в защищённое хранилище (`patient_pseudonym_map`),
   - вычищает PHI-теги DICOM по профилю (DICOM PS3.15 Basic Application Level Confidentiality),
   - перекладывает очищенные объекты в чистый Orthanc и MinIO.
4. **Зеркалирование метаданных** в PostgreSQL на уровне `study` и `series` (пиксели — только в MinIO/Orthanc).
5. Валидация целостности серии, детект дубликатов (по SOPInstanceUID / хешу), автосвязывание пациента через `patient_identifier` с ручным подтверждением при неоднозначности.

## 3. Хранение (раздел 4.2)

| Что | Где |
|---|---|
| Пиксели (DICOM, маски SEG/NIfTI, меши glTF/STL) | MinIO (S3), уровень отдельных изображений — Orthanc |
| Метаданные study/series, находки, аудит, версии моделей | PostgreSQL |
| Идентифицирующая информация (ФИО, номера карт, map) | Защищённое хранилище идентифицирующего контура |

**Пиксельные данные никогда не хранятся в PostgreSQL.**

## 4. Режимы работы (раздел 2)

Режим задаётся на уровне установки и модальности, переключается **только администратором**
с записью в аудит-лог. Реализовано в `app/core/modes.py` и таблице `operating_mode`.

| Режим | Врач видит | Назначение |
|---|---|---|
| `RESEARCH` | Всё, с маркировкой «не для клинического применения» | Разработка, обучение |
| `SHADOW` | Ничего (результаты только в БД) | Накопление статистики |
| `ASSIST` | Черновик, требующий подтверждения | Клиника после валидации |

Новая модель/клиника **всегда** начинает с `SHADOW`. На этапе 1 вся установка в `RESEARCH`.

## 5. Безопасность и аудит

- **Keycloak (OIDC)** — аутентификация, роли: `admin`, `radiologist`, `clinician`, `researcher`, `auditor` (FR-12).
- **Аудит-лог только на добавление** (SR-8): отдельная роль СУБД без прав UPDATE/DELETE на `audit_log`; триггер, запрещающий изменение/удаление. См. миграцию `0002_audit_append_only`.
- Каждый доступ к данным пациента и каждая смена режима логируются.

## 6. Отказоустойчивость (SR-4, НФТ)

- Модуль ИИ изолирован. Его отказ **не влияет** на просмотр и работу с архивом.
- Backend разделён: `viewer/ingest`-путь не зависит от `inference`-воркеров.
- Полная функциональность без интернета (все компоненты — локальные образы).

## 8. Развёртывание

Одна команда (`docker compose up -d`), единая конфигурация через `.env`. Один сервер.
Восстановление БД после аварийного отключения — штатными средствами PostgreSQL (WAL).
Ежедневный бэкап + регулярная проверка восстановления (скрипты `scripts/`).
