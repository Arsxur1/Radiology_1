# Интеграция с PACS: National Children Medical Center

Конкретная конфигурация под площадку (получена из настроек H-PACS,
`Program Setting Information → Network`). Дополняет общий `docs/PACS-INTEGRATION.md`.

## Обнаруженные параметры

| Что | Значение |
|---|---|
| PACS-архив (главный) — AE Title | `HIPACS` |
| PACS-архив — IP | `10.0.0.30` |
| PACS-архив — порт DICOM | `104` |
| Рабочая станция-просмотрщик (H-PACS) | `192.168.13.47` |
| Внешний узел DMED (dcm4chee) | `195.158.10.39:11112` (не используем) |
| Продукт PACS | H-PACS (`C:\PACS\PACSViewer`) |
| Площадка | National Children Medical Center (детский центр) |

## Важно: детская специфика

Центр детский — большая доля педиатрических исследований (возраст 0–13 лет).
Модели, валидированные только на взрослых, будут таким сериям **отказывать**
(SR-7), пока не пройдёт отдельная педиатрическая валидация (раздел 9 ТЗ).
Это ожидаемое поведение, а не ошибка. На этапе пилота педиатрия идёт в накопление
статистики (SHADOW), клинический ИИ-анализ детей — после детской валидации.

## Конфигурация платформы (.env)

```
PACS_AET=HIPACS
PACS_HOST=10.0.0.30
PACS_PORT=104
PACS_LOCAL_AET=MEDVIZ_RAW
PACS_DIRECTION=push
```

**Поток исследований — только push** (PACS пересылает платформе). Автоматический забор
из PACS по расписанию (`pull`) **не реализован**: `PACS_DIRECTION` пока лишь показывается в
настройках (сверка 4 октября). По запросу врача платформа забирает **прошлые** исследования
пациента (C-FIND/C-MOVE, раздел C).

Проверка связи после `make up`:
```
make check-pacs        # ожидаем: C-ECHO успешен
make pacs-connect-check WAIT=15   # все шаги + приём тестового исследования (см. ниже)
```

## Два способа подключить поток исследований

### A. Быстрый тест (push с рабочей станции, без участия IT)

В том же окне `Program Setting Information → Network → Remote Host List` нажать
**Add** и добавить платформу как адресата:

| Поле | Значение |
|---|---|
| Alias | `MEDVIZ` |
| AE Title | `MEDVIZ_RAW` |
| IP | IP сервера платформы (в сети клиники) |
| Port | `4242` |

После этого кнопкой **Send** в списке исследований можно отправить выбранное
исследование на платформу — удобно для первой проверки на нескольких снимках.

### B. Постоянный поток (на архиве HIPACS, силами IT клиники)

Чтобы исследования приходили автоматически, администратор PACS настраивает на
архиве `HIPACS` (10.0.0.30) авто-пересылку (routing/forward) на наш AE
`MEDVIZ_RAW` — например, по модальности (CR/DX, CT, MR). Забор по расписанию со стороны
платформы не реализован (см. выше); если H-PACS не умеет авто-пересылку — сообщить
разработчику, это отдельная доработка.

### D. Заключения обратно в PACS

Подписанное заключение врач отправляет кнопкой **«Отправить в PACS»**: платформа
передаёт DICOM SR (Basic Text SR) по C-STORE на HIPACS, к исходному исследованию
пациента. На HIPACS нужно разрешить приём SR (SOP Class 1.2.840.10008.5.1.4.1.1.88.11)
от AE `MEDVIZ_RAW` и проверить, что просмотрщик PACS показывает кириллицу (UTF-8).

### C. Предыдущие исследования пациента (по запросу врача)

В разборе исследования кнопка **«Найти в PACS»** показывает другие исследования того же
пациента в HIPACS (дата, модальность, описание, число серий — без ФИО и номера карты),
**«Загрузить»** запрашивает выбранное через C-MOVE. Нужно:

- в `.env` заполнены `PACS_AET`, `PACS_HOST`, `PACS_PORT` (как для `make check-pacs`);
- на HIPACS разрешены C-FIND и C-MOVE для AE `MEDVIZ_RAW`, и `MEDVIZ_RAW` прописан
  адресатом C-MOVE (IP платформы, порт 4242) — это тот же узел, что в пункте A;
- поиск идёт по номеру карты из DICOM (PatientID) — он хранится только в
  идентифицирующем контуре; каждый поиск и запрос пишутся в журнал аудита.

## Пошаговая проверка подключения (`make pacs-connect-check`)

Шаги по порядку; на первом неуспешном — причина и что сделать. Данные пациентов не выводятся.

| Шаг | Что проверяет | Типичная причина неуспеха → что сделать |
|---|---|---|
| Настройки | `PACS_AET/HOST/PORT` в `.env` | не заполнены → вписать параметры HIPACS |
| Сеть (TCP) | порт PACS открыт с сервера платформы | таймаут → межсетевой экран / маршрут |
| C-ECHO | PACS принимает наш AE | «calling AE not recognized» → добавить в PACS узел `MEDVIZ_RAW` / IP платформы / 4242; «called AE not recognized» → исправить `PACS_AET` |
| C-FIND | разрешён поиск прошлых исследований | статус ошибки → разрешить C-FIND для `MEDVIZ_RAW` |
| Наш приёмник | orthanc-raw слушает 4242 | не отвечает → `make up`, открыть 4242 для IP PACS |
| Приём от PACS (`WAIT=…`) | тестовое исследование пришло, **обезличено**, исходник удалён из orthanc-raw; есть ли возраст и область | не пришло → узел платформы в PACS; без возраста/области → «Готовность данных площадки» |

Проверено на стенде против Orthanc в роли H-PACS: все шаги ✓, синтетическое исследование
отправлено из H-PACS по C-STORE, принято обезличенным, orthanc-raw пуст.

## Где разместить платформу

Отдельный компьютер/сервер в **той же локальной сети** (например, подсеть
`10.0.0.x` или `192.168.13.x`), с доступом к `10.0.0.30:104`. Требуется Docker.
IP этого сервера и указывается в пункте A как адресат `MEDVIZ_RAW`.

## Порядок первого пилота

1. Поднять платформу на сервере клиники: `make up && make migrate`.
2. Вписать параметры HIPACS в `.env` (см. выше), `make check-pacs` → C-ECHO успешен.
3. Способ A: добавить `MEDVIZ_RAW` в Remote Host List, отправить 2–3 взрослых
   КТ грудной клетки кнопкой Send.
4. Убедиться, что исследования обезличены и видны в рабочем месте врача.
5. Дальше — способ B для постоянного потока и накопление статистики (SHADOW).

## Безопасность

- Обмен PACS↔платформа — только в локальной сети клиники; наружу не выставлять.
- Сменить слабые пароли (в т.ч. учётной записи PACS) до реального потока.
- Все входящие исследования обезличиваются на границе входа (SR-9) до записи в БД.
