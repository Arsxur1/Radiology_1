# Модель данных

Соответствует разделу 5 ТЗ. Все первичные ключи — UUID. Пиксельные данные в БД
не хранятся — только ссылки, метаданные и смыслы.

## Принципы

- **Пациент идентифицируется внутренним UUID.** Номер карты клиники первичным ключом быть не может.
- **Разделение «модель посчитала» / «врач подтвердил».** У каждой находки есть `source` (`model`/`physician`) и `confirmation_status`. Находка от модели не является подтверждённой, пока врач её не подтвердил активным действием (SR-2).
- **Трассируемость** (SR-5): каждый результат модели ссылается на версию модели, хеш весов, входную серию, время, параметры препроцессинга.
- **Аудит только на добавление** (SR-8).
- **Собираемость заключения только вперёд** (FR-8): `report` собирается из `finding`; обратный разбор текста в находки запрещён.

## Сущности

### `patient`
Внутренний UUID — единственный первичный ключ. Пиксельных и идентифицирующих данных не содержит
(ФИО и номера карт — в идентифицирующем контуре).

### `patient_identifier`
Множество написаний ФИО и внешних номеров → один пациент. Решает транслитерацию кириллица/латиница
(актуально для Узбекистана: кириллица / oʻzbek lotin). Хранит историю объединения и разъединения записей.

### `patient_pseudonym_map` (идентифицирующий контур)
Соответствие «реальный идентификатор ↔ обезличенный UUID». **Хранится отдельно** от доверенного контура,
доступ строго ограничен. Никогда не покидает доверенный контур (SR-9).

### `study`
Модальность, дата, аппарат (производитель, модель, версия ПО), протокол. Исходные DICOM неизменяемы.

### `series`
**Толщина среза, размер вокселя, transfer syntax, признак потерь при сжатии.** По этим полям
автоматически определяется пригодность серии для 3D и для конкретной модели (SR-7, FR-5).

### `model_version`
Имя, семантическая версия, хеш весов, дата установки, границы применимости (JSONB), статус
(`shadow` / `active` / `retired`). В `ASSIST` версия зафиксирована; автообновление запрещено технически (SR-3).

### `inference_result`
Ссылка на артефакт, версия модели, время выполнения, метрики (JSONB), идентификатор входной серии,
параметры препроцессинга — полная трассировка (SR-5).

### `correction`
Правка врача: было/стало, тип (`accepted` / `modified` / `rejected`), автор, **затраченное время в секундах**.
Порождается любой правкой маски и любым решением по находке (FR-3, FR-9). Это обучающий сигнал (SR-6).

### `finding`
Код локализации (SNOMED CT либо RadLex), измерения (JSONB), привязка к координатам в серии,
источник (`model`/`physician`), статус подтверждения. Терминология по умолчанию — RadLex (см. VOPROSY-K-TZ.md, п. 28).

### `report`
Собирается из подтверждённых находок. Обратное направление (разбор текста на находки) запрещено.
Каждое предложение трассируется до конкретной `finding` (FR-8).

### `audit_log`
Только добавление. Все действия с данными пациента и все смены режимов. UPDATE/DELETE запрещены
на уровне прав СУБД и триггером (SR-8).

### `data_drift_metric`
Метрики распределения входов и выходов по срезам: аппарат, протокол, возрастная группа (FR-11).

### `operating_mode`
Текущий режим по установке и модальности. Смена — только администратором, с записью в аудит (раздел 2).

## Диаграмма связей (упрощённо)

```
patient 1───* patient_identifier
patient 1───* study 1───* series
series  1───* inference_result *───1 model_version
inference_result 1───* finding *───1 correction
finding *───* report        (report собирается только из подтверждённых finding)
*        ───* audit_log      (append-only, ссылки на любые сущности)
series  1───* data_drift_metric
```

## Заметки по реализации

- Изменяемые схемы (границы применимости, метрики, измерения) — в JSONB.
- Уровень отдельных изображений остаётся за Orthanc; в PostgreSQL зеркалируются `study` и `series`.
- Внешние ключи, индексы по (`patient_id`), (`study_id`), (`modality`, `study_date`), уникальность по DICOM UID.
