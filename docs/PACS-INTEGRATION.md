# Интеграция с внешним PACS (FR-1)

## Принцип: доступ получает ваш сервер, а не облако

Платформа подключается к PACS клиники **на инфраструктуре клиники**, в локальной
сети рядом с PACS. Никакой внешний/облачный доступ к PACS не нужен и не
предусмотрен: идентифицирующие данные (PHI) не должны покидать доверенный контур
(SR-9). Обезличивание происходит на границе входа, до попадания в БД.

```
   [ PACS клиники ]  ──DICOM──►  [ Orthanc raw (AE: MEDVIZ_RAW) ]
        ▲   │                          │  обезличивание (SR-9)
        │   │ C-STORE (push)           ▼
        │   └──────────────────►  [ Orthanc clean + MinIO + PostgreSQL ]
        │
        └── C-FIND/C-MOVE (pull) ◄── платформа (backend, коннектор PACS)
                 или DICOMweb QIDO/WADO
```

## Два способа подключения

### A. PACS → платформа (push, основной путь ТЗ)

В настройках вашего PACS добавьте наш приёмный узел как DICOM-адресата:

| Параметр | Значение по умолчанию |
|---|---|
| AE Title | `MEDVIZ_RAW` |
| Host | IP сервера платформы |
| Port | `4242` |

Затем отправляйте исследования по **C-STORE** (вручную или автопересылкой).
Дальше срабатывает штатный пайплайн: обезличивание → зеркалирование → (при
наличии активной модели) автосегментация.

### B. Платформа → PACS (pull)

Коннектор (`app/services/pacs.py`, API `/pacs/*`, только роль admin):

| Операция | Эндпоинт | Назначение |
|---|---|---|
| C-ECHO | `POST /pacs/echo` | проверить связь с PACS |
| C-FIND / QIDO | `POST /pacs/find` | найти исследования по критериям |
| C-MOVE | `POST /pacs/move` | попросить PACS выгрузить исследование на `MEDVIZ_RAW` |

Для C-MOVE ваш PACS должен знать `MEDVIZ_RAW` как зарегистрированного адресата —
это настраивается в самом PACS. Если PACS поддерживает **DICOMweb**, задайте
`dicomweb_base_url` узла и используйте `use_dicomweb: true` (путь QIDO/WADO).

### Настройка «под ключ» (один файл .env)

Чтобы не передавать параметры PACS в каждом запросе, впишите их один раз в `.env`
(по данным от заказчика — см. таблицу параметров ниже):

```
PACS_AET=PACSSERVER            # AE Title вашего PACS
PACS_HOST=192.168.1.50         # IP PACS (или 127.0.0.1, если платформа на том же ПК)
PACS_PORT=11112                # DICOM-порт (обычно 104 или 11112)
PACS_LOCAL_AET=MEDVIZ_RAW      # наш приёмный AE
PACS_DICOMWEB_URL=             # если есть DICOMweb
PACS_DIRECTION=push            # push | pull
```

Проверка связи одной командой:

```bash
make check-pacs      # показывает конфиг и делает C-ECHO к настроенному узлу
```

Соответствующие эндпоинты: `GET /pacs/config` (показать настройку без секретов),
`POST /pacs/echo/default` (C-ECHO к узлу из `.env`).

### Установка зависимостей коннектора

Классический DICOM-сетевой путь требует `pynetdicom`:

```bash
pip install -e ".[pacs]"
```

DICOMweb-путь работает на `httpx` (уже в основных зависимостях).

## Пример: проверка связи и поиск

```bash
# C-ECHO
curl -X POST http://<сервер>:8000/pacs/echo \
  -H "Content-Type: application/json" \
  -d '{"aet":"REMOTE_PACS","host":"10.0.0.5","port":11112}'

# C-FIND: КТ за дату
curl -X POST http://<сервер>:8000/pacs/find \
  -H "Content-Type: application/json" \
  -d '{"node":{"aet":"REMOTE_PACS","host":"10.0.0.5","port":11112},
       "modality":"CT","study_date":"20260101"}'
```

## Безопасность

- **Смените пароль PACS.** Значение вроде `1` недопустимо для системы с PHI.
- Держите обмен PACS↔платформа в локальной сети; не выставляйте DICOM-порты наружу.
- Все выгруженные исследования обезличиваются на границе входа (SR-9); связь
  «псевдоним ↔ реальные данные» хранится только в изолированном идентифицирующем
  контуре.
- Доступ к коннектору — только роль `admin`; каждое обращение к данным пациента
  логируется в аудит (FR-12).

## Почему нельзя «подключиться из чата»

Ассистент разработки работает в изолированном облачном окружении и **не имеет
сетевого маршрута** к PACS на локальной машине клиники — и не должен иметь.
Интеграция настраивается на вашем сервере по схеме выше; ассистент готовит код и
конфигурацию, а фактический доступ к PACS остаётся внутри контура клиники.
