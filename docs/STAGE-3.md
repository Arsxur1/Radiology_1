# Этап 3: сравнение во времени и черновик заключения

Режим — `RESEARCH`. Обе функции опираются только на подтверждённые врачом
структурированные находки. Сравнение во времени работает **без ИИ** и обязательно
в первой версии (FR-7).

## Сравнение во времени (FR-7)

`services/temporal.py` — чистые детерминированные функции; `temporal_repo.py` —
выборка из БД.

- Находки одного пациента группируются по коду локализации / структуре (не по
  тексту).
- Точки сортируются по дате исследования; считается динамика последней пары:
  абсолютное изменение, процент, направление (рост / снижение / без изменений).
- По умолчанию берутся только подтверждённые находки — динамика строится по тому,
  что подтвердил врач.
- Не использует ИИ-модели (требование FR-7).

API: `GET /temporal/patient/{patient_id}` → ряды по структурам с дельтами.

## Черновик заключения (FR-8)

`services/report_draft.py` (сборка) + `report_repo.py` (БД) + `report_export.py`
(выгрузка).

Инварианты (раздел 11 — при неоднозначности в пользу явного участия врача):

1. **Только подтверждённые находки.** Неподтверждённая находка в наборе → отказ
   (`UnconfirmedFindingError`). Выборка для сборки идёт по `CONFIRMED`.
2. **Рендерер лишь превращает числа и коды в текст.** Он не анализирует
   изображения, не формирует находки, не добавляет утверждений вне
   структурированных данных. По умолчанию — детерминированный шаблон (офлайн,
   воспроизводимо). Локальная LLM может заменить рендерер, получая те же
   структурированные данные и не имея доступа к изображениям (VOPROSY-K-TZ.md, п. 32).
3. **Трассируемость.** Каждое предложение → конкретная находка (`sentence_map`:
   индекс → `finding_id`).
4. **Только вперёд.** Обратный разбор текста в находки не поддерживается — такой
   операции в модуле нет (FR-8).
5. **Финализация — активное действие врача** (SR-2), пишется в аудит
   (`REPORT_FINALIZE`).

### Языки

Русский (по умолчанию), узбекский, английский — подписи и единицы измерения
локализованы. Медицинскую терминологию на узбекском валидирует клиника
(VOPROSY-K-TZ.md, п. 31).

### Выгрузка

- **HTML → PDF:** `GET /reports/{id}/export.html` — самодостаточный HTML,
  печатается в PDF офлайн; тяжёлый рендер PDF подключается на стенде. Выгрузка
  доступна только после финализации.
- **DICOM SR:** дерево содержания строит чистая функция `report_sr.build_sr_content`
  (Basic Text SR: контейнер + текстовые пункты, каждый трассируется до находки через
  TrackingUID); `report_export.build_dicom_sr` сериализует его в DICOM через pydicom на
  стенде. Проверить трассировку без стенда: `GET /reports/{id}/sr-content`.

## API этапа 3

| Метод | Назначение |
|---|---|
| `GET /temporal/patient/{id}` | Динамика подтверждённых находок по времени (FR-7) |
| `POST /reports/generate` | Собрать черновик из подтверждённых находок (FR-8) |
| `GET /reports/{id}` | Черновик с трассировкой предложений |
| `POST /reports/{id}/finalize` | Финализация — активное действие врача (SR-2) |
| `GET /reports/{id}/export.html` | Выгрузка в HTML для печати в PDF |
