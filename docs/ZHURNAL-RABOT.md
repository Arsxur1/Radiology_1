Подробная запись того, что сделано, как проверено и что осталось. Пополняется после
каждого завершённого шага. Коммиты указаны короткими хешами ветки

## Постоянные ограничения (действуют всегда)

- Пароли и данные пациентов не пересылаются в чат и не записываются в документы.
  Пароли сотрудникам — только лично.
- PACS наружу не выставляется: порт DICOM открыт только для H-PACS в сети клиники.
- Слабый пароль PACS меняется до подключения.
- Условия PhysioNet (DUA): изображения, CSV, отчёты и любые записи датасетов не
  загружаются в онлайн-ИИ-сервисы, включая чат разработки. Из обучающего контура
  наружу передаются только сводные `*.report.json` (счётчики и названия меток).
- Режимы: пилот идёт в SHADOW/RESEARCH; результаты теневого прогона врачу не
  показываются никогда; заглушки не выдаются за настоящие модели.
- Туберкулёз — не главный фокус; УЗИ в первую версию не входит.

### 30 сентября — FR-10: гейт продвижения на свидетельствах сервера

- **Проблема.** Раньше цифры для гейта (объём замороженного теста, «лучше
  действующей», доля отклонений, «нет деградации на аппаратах») администратор вводил
  сам — гейт проверял того, кто его и заполнял.
- **Решение** (`services/model_registry.py`: `collect_evidence`, `gate_for`,
  `record_frozen_evaluation`; миграция 0011 `model_version.evidence`):
  - замороженный тест — только из отчёта `cli evaluate`, и только если `weights_hash`
    отчёта совпадает с весами модели (чужой отчёт не подложить);
  - превосходство — средний AUROC кандидата выше, чем у действующей модели **на том же**
    замороженном тесте (по дайджесту); если сравнить не с чем — гейт закрыт;
  - доля расхождений — из теневого прогона против подписанных заключений; меньше 100
    проверенных врачом случаев — данных недостаточно;
  - деградация — срезы по аппаратам **и по возрастным группам детей**: срез от 20 случаев
    с долей расхождений выше порога закрывает гейт, даже если в среднем всё хорошо;
  - администратор вводит только обоснование; свидетельства на момент решения пишутся
    в журнал аудита вместе с ним.
- API: `POST /models/{id}/evaluate` (без тела), `POST /models/{id}/frozen-evaluation`,
  `POST /models/{id}/promote` (`{justification}`). Админка: вместо полей ввода —
  таблица собранных свидетельств и загрузка отчёта замороженного теста.
- Проверено: `test_promotion_evidence.py` (7 тестов): чужие веса отклоняются; без
  свидетельств гейт закрыт; хороший кандидат проходит; деградация у младенцев
  блокирует при хорошем среднем; деградация на одном аппарате блокирует; кандидат
  обязан превзойти действующую модель на том же тесте; цифры, присланные клиентом,
  игнорируются. Всего тестов backend: 234.

### 30 сентября — FR-4: совмещённая серия в просмотрщике

- Раньше результат совмещения оставался файлом преобразования и картинкой-шахматкой;
  врач не мог прокручивать совмещённые серии вместе.
- Теперь после подтверждения качества кнопка «Показать совмещённую серию в
  просмотрщике»: воркер пересчитывает совмещаемую серию (например, МРТ) на сетку

  исследования — тот же FrameOfReferenceUID и геометрия срезов, поэтому OHIF
  прокручивает их синхронно и может накладывать. Серия помечена как производная

  детерминированы — повторная публикация заменяет ту же серию; копия в S3
  (`registered/`) — восстановление из бэкапа пересобирает и её.
- Публикуется только подтверждённое совмещение (иначе 409) и только рентгенологом.
- Проверено на фантоме (`test_registration.py`): серия читается обратно стандартным
  DICOM-читателем с той же геометрией (размер, шаг, начало координат), содержимое
  совпадает с опорной (корреляция > 0,95); повтор даёт те же UID; неподтверждённое —
  409, исследователь — 403. Всего тестов совмещения: 15.

### 1 октября — рабочий список: очередь неописанных на сервере

  позавчерашнее исследование в очередь не попадало вовсе.

### 1 октября — пиковый приём: 4 КТ одновременно

- Сценарий «утренний пакет из H-PACS»: 4 исследования КТ разных пациентов по 112 срезов
  (448 срезов) отправлены по C-STORE одновременно, 4 соединения; воркер — 2 потока на CPU
  (в compose число потоков по умолчанию равно числу ядер).
- **Приём:** все 448 срезов обезличены и записаны в хранилище за **37 с** (~12 срезов/с);
  в orthanc-raw исходников с ФИО не осталось.
- **Анализ:** запуск анализа откладывается до конца серии — 448 отложенных задач (по
  срезу) свелись ровно к **4** задачам сегментации, по одной на серию; у каждой серии
  ровно один прогон TotalSegmentator и ровно один отказ демо-модели грудной клетки (область
  «живот» вне её применимости, SR-7). Все 4 КТ проанализированы через **181 с** после
  начала отправки.
- Дефектов не найдено.

### 1 октября — приём не теряет снимки при сбое хранилища

- **Найдено (воспроизведено вживую):** задача приёма делала 3 повтора по 10 с. Хранилище
  недоступно 60 с (перезапуск при обновлении) → одиночный снимок (типичный рентген)
  исчерпывал повторы, оставался в orthanc-raw, а курсор наблюдателя уже ушёл вперёд —
  **исследование молча не появлялось у врача**. КТ из 112 срезов в той же ситуации
  дошла лишь потому, что очередь из 112 задач растянула окно повторов.
- **Сделано:**
  - повторы с растущей паузой 10 с → 10 мин, до 10 попыток (~50 мин);
  - досылка в наблюдателе: раз в 5 мин (и сразу при запуске) снимки, пролежавшие в
    orthanc-raw дольше 10 мин, отправляются на обработку заново (приём идемпотентен);
    не больше 6 раз на снимок — битый файл не крутится бесконечно;
  - «Состояние системы»: новая проверка «застрявшие в orthanc-raw» (это исходники с ФИО).
- **Проверено вживую:** до исправления — 0 из 1, снимок застрял; после — тот же снимок
  дослан автоматически («Досылка застрявших снимков orthanc-raw: redispatched 1») и
  появился у врача, orthanc-raw пуст. Тесты: окно повторов > 40 мин, «застрявший» —
  только старше 10 мин, досылка и остановка после лимита.

### 1 октября — «Состояние системы»: место на диске

- Риск: снимки за год занимают сотни ГБ; когда место кончится, остановятся приём, базы и
  бэкап — раньше об этом ничто не предупреждало.
- Проверка «Диск с данными»: свободное место на диске томов docker (через том приёма):
  < 15 % или < 50 ГБ — предупреждение, < 5 % или < 10 ГБ — приём «не работает».
- Проверено вживую: стенд показал «свободно 13 ГБ из 252 ГБ (5 %) — пора расширять диск»,
  приём — «требует внимания», просмотр — работает. Тест порогов.

### 1 октября — точечная проверка безопасности и живучесть шлюза

- **CSV-инъекция в выгрузке журнала аудита:** ячейка, начинающаяся с `= + - @`, в Excel
  исполнялась бы как формула (например, имя пользователя `=HYPERLINK(...)`). Теперь такие
  ячейки экранируются апострофом (`routes_audit.csv_safe`); тест с `=cmd|...`.
- **Возврат после входа:** уже был безопасен (адрес в sessionStorage, проверка `state`,
  внутренний маршрутизатор); добавлена страховка — только внутренние пути (`/…`, не `//…`).
- **Отладочный вход (`ALLOW_DEBUG_AUTH`):** по умолчанию выключен, но при ошибке настройки
  любой в сети стал бы администратором заголовком. Теперь шлюз вырезает `X-Debug-*` для
  API и проверки снимков, а «Состояние системы» при включённом флаге — «не работает» с
  причиной. Проверено вживую при включённом флаге: через шлюз — 401 (API и DICOMweb),
  напрямую на самом сервере — 200.
- **Найдено вживую: шлюз не стартовал без OHIF.** После перезапуска Docker контейнер
  просмотрщика не поднялся, и nginx упал целиком («host not found in upstream ohif») —
  врачи потеряли бы рабочее место, API и снимки из-за вспомогательного просмотрщика (то же
  с Keycloak при его перезапуске). Теперь Keycloak и OHIF адресуются через переменные и DNS
  docker (имя разрешается при запросе): шлюз стартует всегда; без OHIF/Keycloak интерфейс и
  API работают (200), их пути дают 502, а после их запуска всё восстанавливается **без
  перезапуска шлюза** — проверено на стенде для обоих. Локальный прогон шагов CI шлюза
  (HTTP и HTTPS) — успешно. Всего тестов backend: 267.
