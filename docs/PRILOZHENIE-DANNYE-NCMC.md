# Приложение к договору с NCMC: техническое описание обработки данных

**Проект для юристов сторон.** Описывает, как платформа обрабатывает данные пациентов
Национального детского медицинского центра (NCMC). Каждое утверждение соответствует
коду платформы (ссылки — для инженеров сторон). Юридические формулировки, основания
обработки и сроки — за юристами; места, требующие решения, отмечены **«Решить»**.

Редакция от 2 октября 2026 г.

## 1. Назначение обработки

1. **Поддержка врача-рентгенолога:** находки-черновики ИИ на рентгенограммах, КТ и МРТ,
   измерения, сравнение с прошлыми исследованиями, черновик заключения. Каждая находка
   включается в заключение только активным действием врача; решения на основании одних
   выводов ИИ не принимаются (SR-2; закон РУз ЗРУ-1115).
2. **Улучшение моделей на данных площадки:** решения врачей (подтверждение, исправление,
   отклонение находок, подписанные заключения) служат обучающими метками для калибровки и
   дообучения моделей под пациентов NCMC (FR-9, FR-10).
3. **Контроль качества и безопасности:** журнал аудита, контроль дрейфа, сводная статистика
   пилота (только агрегаты).

**Решить:** правовое основание обработки для п. 2 (согласие законных представителей,
иное основание по закону ЗРУ-547, решение этического комитета NCMC).

## 2. Какие данные поступают

Источник — PACS NCMC (H-PACS): исследования передаются по протоколу DICOM на сервер
платформы в сети NCMC (порт 4242 открыт только для адреса PACS).

| Данные | Где хранятся | Кто видит |
|---|---|---|
| Снимки и метаданные DICOM (аппарат, протокол, параметры, возраст, пол, даты) — **обезличенные** | доверенный контур: БД `medviz`, хранилище снимков, просмотрщик | врачи, клиницисты, администраторы, исследователи (только обезличенное) |
| ФИО, номер карты (MRN), исходные UID исследований | **идентифицирующий контур:** отдельная БД `medviz_idmap` | только при «раскрытии личности» (п. 4) |
| Решения врачей, заключения, журнал аудита | доверенный контур | по ролям (п. 5) |

Исходный объект с ФИО попадает в приёмный узел (`orthanc-raw`) и **удаляется сразу после
обезличивания** (`RAW_DELETE_AFTER_INGEST=true`); оригинал остаётся в PACS NCMC.

## 3. Обезличивание (псевдонимизация) — `services/anonymization.py`

- Удаляются: ФИО, номер карты и другие ID пациента, адрес, телефоны, дата и время рождения,
  ФИО и данные врачей и операторов, учреждение, отделение, станция, номер направления
  (Accession), серийный номер аппарата, ID исследования и процедур — полный перечень в
  `TAGS_TO_REMOVE`; **все приватные теги производителей**, кривые и оверлеи (там бывают надписи).
- Заменяются: идентификатор пациента и UID исследования/серии/снимка — на псевдонимы,
  вычисляемые **HMAC-SHA256 с секретным ключом площадки** `PSEUDONYM_KEY`
  (`app/core/pseudonym.py`). Без ключа псевдоним необратим, в том числе перебором номеров
  карт. Ключ хранится только на сервере платформы и в зашифрованной резервной копии.
- В доверенном контуре нет ни ФИО, ни номера карты, даже для сопоставления пациентов:
  сопоставление идёт по ключевым токенам (с 2 октября 2026 г., миграция 0014).
- Сохраняются (нужны для анализа и безопасности модели): модальность, аппарат и его
  модель, протокол, параметры съёмки, **возраст на момент исследования** (дата рождения
  удаляется), пол, **даты исследования**.

**Важно для договора:** это **псевдонимизация**, а не анонимизация. Связь «псевдоним ↔
пациент» существует (в идентифицирующем контуре), поэтому данные доверенного контура
остаются персональными по смыслу закона. Анонимными (не персональными) являются только
сводные отчёты (п. 7).

### Ограничения (известные, с мерами)

| Ограничение | Мера |
|---|---|
| **Текст, впечатанный в пиксели снимка** (ФИО на снимке — бывает на некоторых аппаратах, чаще на вторичных копиях экрана), из изображения не удаляется | Платформа распознаёт риск по DICOM (флаг BurnedInAnnotation=YES или вторичная копия экрана — Secondary Capture): такие серии **не идут в обучение и внешние отчёты**, врач видит предупреждение, «Готовность данных площадки» показывает их число по аппаратам. Аппарат, который впечатывает ФИО без флага, так не распознаётся — NCMC проверяет настройки аппаратов при подключении. **Решить:** запрещать ли приём вторичных копий совсем |
| Даты исследований сохраняются (нужны для сравнения в динамике) | Доступ к доверенному контуру — только по ролям в сети NCMC; в выгрузках для обучения даты не нужны |
| Редкие сочетания (возраст + пол + редкая находка + дата) теоретически могут указать на ребёнка | Сводные отчёты показывают редкие строки только от 5 исследований; построчные данные из NCMC не выносятся (п. 7) |

## 4. Раскрытие личности пациента

ФИО и номер карты показываются врачу только для действий, которым они нужны, с указанием
цели и записью в журнал аудита (`GET /studies/{id}/identity`): подписание и передача
заключения, клиническое решение, сопоставление с прошлыми исследованиями в PACS. Роли:
врач-рентгенолог, клиницист.

## 5. Доступ сотрудников и учёт действий

- Вход только по учётным записям NCMC (Keycloak на сервере платформы): защита от подбора
  пароля, политика паролей, ограничение сессий. Пароли выдаются сотрудникам лично.
- Роли: администратор, врач-рентгенолог, клиницист, исследователь (только обезличенные
  данные), аудитор (только журналы).
- **Журнал аудита:** каждое открытие исследования, раскрытие личности, решение по находке,
  подпись, выгрузка, смена модели — с автором и временем. Журнал только на добавление (права
  СУБД), записи связаны хеш-цепочкой; целостность проверяется (`/audit/verify`).
- Доступ к системе — только из сети NCMC через шлюз HTTPS; внутренние порты наружу не
  открыты.

## 6. Где хранятся данные и резервные копии

- Все данные — **на сервере платформы в сети NCMC** (Узбекистан). Внешние облачные сервисы
  не используются. (С 27.03.2026 обязательная локализация в РУз касается биометрических и
  генетических данных; медицинские снимки обрабатываются в РУз в любом случае.)
- Ночные резервные копии на отдельный диск NCMC; **все базы данных** (доверенный и
  идентифицирующий контуры, учётные записи сотрудников) и ключ псевдонимизации — **только
  в зашифрованном виде** (AES-256, ключ бэкапа хранится отдельно от копий). Обезличенные
  снимки в копии не шифруются платформой (объём) — **диск для копий должен быть
  зашифрован** средствами ОС (рекомендация NCMC). Хранится 14 последних копий (`BACKUP_KEEP`).
- **Решить:** сроки хранения обезличенных снимков, решений врачей и журнала аудита; порядок
  удаления по окончании договора.

## 7. Что покидает NCMC

| Что | Куда | Содержит ли персональные данные |
|---|---|---|
| Подписанное заключение (DICOM SR) с отметкой об участии ИИ | **в PACS NCMC** к исходному исследованию | да — это медицинская документация NCMC, остаётся в NCMC |
| Сводные отчёты: «Пилот», «Готовность данных площадки», отчёты обучения `*.report.json` | разработчику (по согласию NCMC) | нет — только счётчики и доли; редкие строки описаний скрыты, цифры заменены |
| Метки площадки и обезличенные снимки для дообучения (`/learning/site-manifest`, роль исследователь/администратор, запись в аудит) | **обучающий сервер** | псевдонимизированные данные (п. 3) |

**Решить:** где стоит обучающий сервер. Рекомендуемый вариант — **в сети NCMC** (тогда
псевдонимизированные данные не покидают клинику). Если за пределами NCMC — нужны
договорные гарантии и оценка трансграничной передачи по закону ЗРУ-547.

## 8. Модели ИИ и маркировка

- Модели работают на сервере платформы, снимки во внешние ИИ-сервисы не передаются.
- Новая версия модели сначала работает **в теневом режиме** (врач её не видит) и
  становится рабочей только после проверки на данных NCMC и документированного решения
  ответственного лица; откат — мгновенный (FR-10).
- Модели, обученные на данных «только для исследований», в клиническую работу не
  допускаются (проверка встроена в платформу; `ISTOCHNIKI-I-PRAVO.md`).
- Заключение с находками ИИ маркируется: модель и версия, пометка у каждого пункта
  «ИИ → подтверждено врачом» (закон РУз ЗРУ-1115).

## 9. Обязанности сторон (технические)

**NCMC:** настроить PACS на передачу исследований на сервер платформы; сменить слабый
пароль PACS до подключения; выдать учётные записи сотрудникам лично; сгенерировать и
сохранить ключи (`PSEUDONYM_KEY`, ключ бэкапа); проверить, что аппараты не впечатывают
ФИО в снимки.

**Разработчик:** не запрашивать и не получать построчные данные пациентов за пределы
NCMC без отдельного основания; предоставлять обновления платформы с журналом изменений;
сообщать о найденных уязвимостях и их исправлении (пример — ключевая псевдонимизация,
2 октября 2026 г., `ZHURNAL-RABOT.md`).

**Инциденты:** в платформе есть журнал инцидентов — сотрудник NCMC сообщает со страницы
исследования (вид из списка, в том числе «раскрытие персональных данных»); описание хранится
в доверенном контуре, ФИО в него писать не нужно (исследование привязывается само); в журнал
аудита попадает только факт, вид и тяжесть. Разработчику передаётся лишь сводка по видам
(отчёт «Пилот»).

**Решить:** порядок уведомления об инцидентах и сроки (кто кому и за сколько часов, в том
числе об утечке персональных данных); ответственный за обработку персональных данных в
NCMC; ответственный за разбор инцидентов (роль администратора в платформе).
