# Платформа анализа медицинских изображений

Платформа приёма, хранения, просмотра и (в последующих этапах) ИИ-анализа исследований
КТ, МРТ и рентгенографии в формате DICOM с самообучающимся контуром развития моделей.

Реализация ведётся строго по ТЗ (`TZ-platforma-medicinskoy-vizualizacii.md`). Открытые вопросы
к заказчику — в `VOPROSY-K-TZ.md`.

> **Статус:** Этапы 1–2 (RESEARCH). Приём, обезличивание, хранение, модель данных, права, аудит;
> самообучающийся контур (захват правок, экспорт, развитие моделей, дрейф);
> сегментация КТ грудной клетки с гейтом применимости и детерминированными измерениями;
> сравнение во времени (без ИИ) и черновик заключения из подтверждённых находок.
> См. `docs/LEARNING-LOOP.md`, `docs/STAGE-2.md`, `docs/STAGE-3.md`.
> Система **не ставит диагноз** и **не заменяет врача**. Ни один вывод модели не попадает
> в медицинскую документацию без явного подтверждения врача.

## Согласованные решения (см. VOPROSY-K-TZ.md)

| Вопрос | Решение |
|---|---|
| УЗИ (УЗД) | Не в первой версии. Модель данных не ограничивает `modality`, задел на v2. |
| Юрисдикция | Узбекистан (регистрация медизделия РУз, ЗРУ-547 о персональных данных). |
| Первая клиническая область | КТ грудной клетки → КТ брюшной полости → МРТ головного мозга → рентген грудной клетки. |
| Старт | Этап 1 в режиме RESEARCH. |

## Архитектура (компоненты из ТЗ, раздел 4)

| Слой | Компонент |
|---|---|
| DICOM-узел | Orthanc (C-STORE, C-FIND, DICOMweb) |
| Объектное хранилище | MinIO (S3-совместимое) |
| Метаданные | PostgreSQL 16 (+ JSONB) |
| Очередь задач | Celery + Redis |
| Backend API | FastAPI (Python) |
| Просмотр | OHIF Viewer (Cornerstone3D) |
| Аутентификация | Keycloak (OIDC, RBAC) |
| Развёртывание | Docker Compose, одна команда |
| Мониторинг | Prometheus + Grafana (задел) |

Подробнее — `docs/ARCHITECTURE.md` и `docs/DATA-MODEL.md`.
Сводка по системе для заказчика и регулятора — `docs/OBZOR-SISTEMY.md`.

## Ключевые принципы (ТЗ, раздел 11)

1. **Пиксельные данные никогда не хранятся в PostgreSQL.** Изображения, маски, меши — в MinIO/Orthanc; в БД только ссылки и смыслы.
2. **Обезличивание на границе входа** (SR-9). Идентифицирующие данные не покидают доверенный контур; таблица сопоставления — в отдельном защищённом хранилище.
3. **Аудит-лог только на добавление** (SR-8). Изменение и удаление невозможны на уровне прав СУБД.
4. **Отказ ИИ ≠ отказ просмотра** (SR-4). Недоступность модели переводит систему в режим обычного просмотрщика.
5. **Разделение «система посчитала» / «врач подтвердил»** — на уровне модели данных и интерфейса.

## Быстрый старт

```bash
cp .env.example .env      # отредактируйте секреты
make up                   # или: docker compose up -d --build
make migrate              # применить миграции БД
make seed                 # (опционально) демо-данные для показа без PACS/GPU
```

Сервисы после запуска:

| Сервис | URL |
|---|---|
| Backend API (Swagger) | http://localhost:8000/docs |
| OHIF Viewer | http://localhost:3000 |
| Orthanc | http://localhost:8042 |
| MinIO Console | http://localhost:9001 |
| Keycloak | http://localhost:8080 |

## Разработка

```bash
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest          # unit + интеграционные + приёмочные (docs/ACCEPTANCE.md)
ruff check .
```

Тесты гоняются на in-memory SQLite через переносимые типы (`app/db/types.py`):
модели те же, что в продакшне на PostgreSQL. CI (`.github/workflows/ci.yml`)
на каждый push прогоняет два job: **backend** (ruff + pytest) и **frontend**
(`npm ci` + строгая сборка `tsc -b && vite build`).

## Структура репозитория

```
backend/            FastAPI-приложение, воркеры Celery, миграции
  app/
    api/            HTTP-роуты
    core/           конфиг, безопасность, режимы работы
    db/             сессия, базовые классы
    models/         ORM-модели (модель данных ТЗ, раздел 5)
    schemas/        Pydantic-схемы
    services/       обезличивание, приём, аудит, хранилище
    workers/        задачи Celery
  alembic/          миграции БД
deploy/             docker-compose, Makefile-хелперы
infra/              конфиги Orthanc, Keycloak, Postgres
frontend/           конфигурация OHIF Viewer
docs/               архитектура, модель данных
scripts/            вспомогательные скрипты
```

## Лицензии моделей и данных

Клинический режим ASSIST требует проверки лицензий конкретных весов моделей
(TotalSegmentator, nnU-Net, MedSAM) и, при необходимости, дообучения собственных
весов на собранных данных (см. VOPROSY-K-TZ.md, п. 34). На этапе 1 модели не подключаются.
