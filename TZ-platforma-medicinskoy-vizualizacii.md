## 1. Назначение системы

Система принимает исследования КТ, МРТ и рентгенографии в формате DICOM, выполняет автоматическую сегментацию анатомических структур, совмещение разных модальностей одного пациента, построение трёхмерных моделей, количественные измерения и сравнение с предыдущими исследованиями, после чего формирует структурированный черновик заключения для подтверждения врачом.

Отдельная и равная по значимости задача системы — **накопление размеченных данных из клинической работы** и управляемое улучшение моделей на этой основе.

### 1.1. Чем система не является

Формулировки ниже — не оговорки, а проектные ограничения, определяющие архитектуру.

- Система **не ставит диагноз** и не формирует диагностическое заключение самостоятельно.
- Система **не принимает решений о лечении** и не даёт рекомендаций по терапии.
- Ни один вывод модели не становится частью медицинской документации без явного подтверждения врача.
- Система не заменяет врача-рентгенолога и проектируется как инструмент, сокращающий его рутинную работу.

### 1.2. Целевая популяция

Взрослые и дети. **Требование:** все модели, пороги и границы применимости валидируются для взрослых и педиатрических пациентов раздельно. Модель, валидированная только на взрослых, должна автоматически отказывать в анализе педиатрического исследования (см. SR-7), а не выдавать результат с оговоркой.

## 2. Режимы работы системы

Ключевой архитектурный механизм. Режим задаётся **на уровне установки и модальности**, переключается только администратором с записью в аудит-лог.

| Режим | Что видит врач | Назначение |
|---|---|---|
| `RESEARCH` | Всё, с явной маркировкой «не для клинического применения» | Разработка, обезличенные данные, обучение персонала |
| `SHADOW` | **Ничего.** Модель работает, результаты пишутся в БД, но не отображаются | Накопление статистики и сравнение с реальными заключениями до допуска к работе |
| `ASSIST` | Результаты видны как черновик, требующий подтверждения | Клиническое применение после валидации |

**Требование:** новая модель или новая клиника **всегда** начинает с `SHADOW`. Переход в `ASSIST` возможен только при выполнении критериев из раздела 9 и оформляется как отдельное решение с подписью ответственного лица.

## 3. Требования безопасности пациента

Приоритет выше функциональных требований. При конфликте реализуется требование безопасности.

| ID | Требование |
|---|---|
| SR-1 | Система не выводит формулировок диагноза. Только находки, измерения и степень уверенности |
| SR-2 | Включение результата ИИ в заключение — **активное действие врача**. Согласие по умолчанию, авто-принятие и «принять всё» запрещены |
| SR-3 | В режиме `ASSIST` версия модели зафиксирована. Автоматическое обновление модели запрещено технически, а не организационно |
| SR-4 | Отказ или недоступность модели переводит систему в режим обычного просмотрщика. Блокировка доступа к изображениям при сбое ИИ недопустима |
| SR-5 | Каждый результат трассируется: версия модели, хеш весов, идентификатор входной серии, время, параметры препроцессинга |
| SR-6 | Врач может отклонить результат целиком одним действием, и это фиксируется как обучающий сигнал |
| SR-7 | **Отказ при выходе за границы применимости.** Если серия не соответствует валидированному диапазону (толщина среза, возраст, модальность, наличие контраста, производитель аппарата), система возвращает явный отказ с указанием причины. Выдача результата «с пониженной уверенностью» вне валидированного диапазона запрещена |
| SR-8 | Аудит-лог только на добавление. Изменение и удаление записей невозможно на уровне прав СУБД |
| SR-9 | Обезличивание выполняется на границе входа. Данные с идентификаторами не покидают доверенный контур |

## 4. Архитектура

### 4.1. Принцип: не изобретать основание

Перечисленные компоненты используются как есть. Собственная реализация любого из них требует письменного обоснования.

| Слой | Компонент |
|---|---|
| DICOM-узел | Orthanc (C-STORE, C-FIND, DICOMweb: WADO-RS / QIDO-RS / STOW-RS) |
| Хранение объектов | MinIO (S3-совместимое) |
| Метаданные | PostgreSQL 16+, JSONB для изменяемых схем |
| Очередь задач | Celery + Redis, либо Temporal при росте сложности пайплайнов |
| Сегментация | TotalSegmentator, MONAI Model Zoo, nnU-Net; MedSAM / SAM-Med3D для интерактивной |
| Фреймворк ИИ | MONAI (PyTorch). Упаковка моделей — MONAI Deploy (MAP) |
| Регистрация | SimpleITK / Elastix либо ANTs. Метрика для разных модальностей — mutual information |
| Меши | VTK (marching cubes), trimesh / PyMeshLab для дециматии и сглаживания |
| Просмотр 2D / MPR / VR | OHIF Viewer на Cornerstone3D |
| Просмотр мешей | VTK.js либо three.js |
| Фронтенд | React + TypeScript, Vite |
| Аутентификация | Keycloak (OIDC), RBAC |
| Развёртывание | Docker Compose, одна конфигурация, установка одной командой |
| Мониторинг | Prometheus + Grafana, включая метрики качества моделей |

### 4.2. Разделение хранения

**Пиксельные данные никогда не хранятся в PostgreSQL.** Изображения, маски и меши — в объектном хранилище; в БД только ссылки, метаданные и смыслы. Уровень отдельных изображений остаётся за Orthanc; в PostgreSQL зеркалируются исследование и серия для поиска и аналитики.

## 5. Модель данных

Минимальный обязательный набор. Ключи — UUID.

| Сущность | Обязательные особенности |
|---|---|
| `patient` | Внутренний UUID как единственный первичный ключ. Номер карты клиники первичным ключом быть не может |
| `patient_identifier` | Множество написаний ФИО и внешних номеров → один пациент. История объединения и разъединения записей. Решает проблему транслитерации кириллица/латиница |
| `study` | Модальность, дата, аппарат (производитель, модель, версия ПО), протокол |
| `series` | **Толщина среза, размер вокселя, transfer syntax, признак наличия потерь при сжатии.** По этим полям автоматически определяется пригодность серии для 3D и для конкретной модели |
| `model_version` | Имя, семантическая версия, хеш весов, дата установки, границы применимости в JSONB, статус (`shadow` / `active` / `retired`) |
| `inference_result` | Ссылка на артефакт, версия модели, время выполнения, метрики в JSONB |
| `correction` | Правка врача: было / стало, тип (принято / изменено / отклонено), автор, **затраченное время в секундах** |
| `finding` | Код локализации (SNOMED CT либо RadLex), измерения в JSONB, привязка к координатам в серии, источник (модель / врач), статус подтверждения |
| `report` | Собирается из находок. Обратное направление — разбор текста на находки — запрещено |
| `audit_log` | Только добавление. Все действия с данными пациента и все смены режимов |
| `data_drift_metric` | Метрики распределения входов и выходов по срезам: аппарат, протокол, возрастная группа |

## 6. Функциональные требования

### FR-1. Приём данных
Приём по C-STORE от модальностей и загрузка вручную. Обезличивание на входе с сохранением сопоставления в отдельном защищённом хранилище. Валидация целостности серии, обнаружение дубликатов, автоматическое связывание с существующим пациентом через `patient_identifier` с ручным подтверждением при неоднозначности. Резервный путь приёма из сетевой папки для аппаратов без Storage SCU.

### FR-2. Просмотр
Осевые, коронарные и сагиттальные проекции, MPR, оконные преcеты по модальности, объёмный рендер, синхронизация серий по позиции, сравнение с предыдущим исследованием в связанных окнах.

### FR-3. Сегментация
Автоматическая по расписанию после приёма. Интерактивная правка масок с кистью, лассо и распространением по срезам. **Любая правка порождает запись `correction`.** Хранение масок в формате DICOM SEG либо NIfTI со ссылкой на исходную серию.

### FR-4. Совмещение модальностей
Последовательность: жёсткая → аффинная → деформируемая. Метрика для разных модальностей — mutual information. Обязательный вывод количественной оценки качества совмещения и **визуальная проверка врачом с возможностью отклонить результат**. Совмещение с неподтверждённым качеством не используется для измерений.

### FR-5. Трёхмерные модели
Построение из подтверждённых масок: marching cubes → сглаживание → дециматия. Экспорт glTF (с сжатием Draco) для веба и STL для печати. **Требование:** при толщине среза, недостаточной для корректной геометрии, система отказывает в построении с указанием причины, а не строит модель с артефактами.

### FR-6. Измерения и находки
Объёмы, линейные размеры, плотностные характеристики, соотношения. Все измерения детерминированы и воспроизводимы: повторный запуск на той же серии той же версией даёт тот же результат.

### FR-7. Сравнение во времени
Автоматическое сопоставление находок между исследованиями одного пациента, расчёт динамики, построение графиков изменения по времени. Функция работает без участия ИИ-моделей и является обязательной в первой версии.

### FR-8. Черновик заключения
Формируется **только из подтверждённых структурированных находок**. Языковая модель выполняет единственную функцию — превращает готовые числа и коды в связный текст. Она не анализирует изображения, не формирует находки и не добавляет утверждений, отсутствующих в структурированных данных. Каждое предложение черновика трассируется до конкретной записи `finding`. Выгрузка в DICOM SR и PDF.

### FR-9. Захват обучающих данных
Требование к интерфейсу: врач **не размечает данные, он работает**, а разметка получается как побочный результат. Каждое подтверждение, изменение и отклонение сохраняется вместе с исходными данными и версией модели. Экспорт обучающего набора с фильтрами по модальности, аппарату, возрасту и качеству разметки.

### FR-10. Контур развития моделей

Обязательная последовательность. Пропуск этапов не допускается.

1. **Фиксация.** Модель в `ASSIST` неизменна. Обновление невозможно без прохождения всей процедуры.
2. **Накопление.** Данные копятся через FR-9.
3. **Дообучение офлайн** по расписанию, на отдельном контуре, порождает модель-кандидата. Обучение на продуктивном контуре запрещено.
4. **Замороженный тест.** Тестовый набор формируется до начала обучения и не открывается никогда. По возможности содержит исследования с аппаратов, отсутствующих в обучающем наборе.
5. **Теневой прогон.** Кандидат работает в `SHADOW` параллельно действующей модели на живом потоке. Результаты сравниваются с заключениями врачей.
6. **Продвижение** — осознанное документированное действие ответственного лица при превосходстве кандидата на замороженном тесте и в теневом прогоне. Обязателен механизм мгновенного откáта к предыдущей версии.

Эта схема соответствует признанному подходу к изменяемым медицинским алгоритмам (предварительно согласованный план изменений, PCCP). Соблюдение её с самого начала — условие возможности будущей регистрации, а не бюрократия.

### FR-11. Контроль дрейфа
Мониторинг распределения входных данных: новый аппарат, изменённый протокол, смещение возрастного состава — с оповещением. Мониторинг доли отклонённых врачом результатов по срезам: рост доли отклонений на конкретном аппарате означает деградацию, которую нельзя обнаружить по общей метрике. Раздельные метрики качества по каждой клинике.

### FR-12. Роли и аудит
Роли: администратор, врач-рентгенолог, клиницист (просмотр и подтверждённые заключения), инженер-исследователь (только обезличенные данные), аудитор (только чтение журналов). Полный журнал доступа к данным пациентов.

## 8. Границы первой версии

**Не входит:** самостоятельная диагностика и классификация патологии; мобильное приложение; облачный мультитенант; обучение моделей с нуля; доработки под отдельного заказчика; любая функция, влияющая на назначение лечения.

**Порядок реализации:**

| Этап | Содержание | Режим |
|---|---|---|
| 1 | Приём, обезличивание, хранение, модель данных, просмотр, права, аудит | `RESEARCH` |
| 2 | Сегментация, измерения, 3D и экспорт, захват правок | `RESEARCH` |
| 3 | Сравнение во времени, структурированные находки, черновик заключения | `RESEARCH` |
| 4 | Развёртывание на пилотной площадке, накопление статистики | `SHADOW` |
| 5 | Локальное валидационное исследование | `SHADOW` |
| 6 | Совмещение модальностей; допуск к клиническому применению по результатам этапа 5 | `ASSIST` |
| 7 | Контур дообучения и контроль дрейфа | `ASSIST` |

## 9. Критерии допуска к клиническому применению

Переход из `SHADOW` в `ASSIST` возможен только при одновременном выполнении:

1. Проведено локальное валидационное исследование на данных пилотной площадки, отдельно для взрослых и детей.
2. Определены и зафиксированы в `model_version` границы применимости; вне них система отказывает (SR-7).
3. Продемонстрировано отсутствие деградации на аппаратах, не участвовавших в обучении.
4. Реализованы и проверены все требования раздела 3 без исключений.
5. Получено заключение о регуляторном статусе системы в юрисдикции применения и выполнены вытекающие из него требования.
6. Персонал обучен, включая понимание границ применимости и порядка действий при отказе системы.
7. Определён ответственный за клиническое применение и порядок разбора инцидентов.

---

## 10. Критерии приёмки

Помимо функциональных, обязательны:

- Полная трассируемость: для любого результата в системе восстанавливается версия модели, входные данные и все правки.
- Воспроизводимость: повторный запуск фиксированной версии на той же серии даёт идентичный результат.
- Проверка отказа: серии вне границ применимости получают отказ, а не результат.
- Проверка деградации: при принудительном отключении модуля ИИ просмотр и работа с архивом сохраняются полностью.
- Невозможность подмены аудит-лога средствами приложения.
- Восстановление системы из резервной копии на чистом сервере в пределах согласованного времени.

## 11. Замечание для исполнителя

Основной риск проекта — не сложность моделей, а нарушение разделения между «система посчитала» и «врач подтвердил». Если это разделение размывается в интерфейсе или в модели данных, система становится непригодной к клиническому применению независимо от качества алгоритмов. При любой неоднозначности требований трактовать в пользу более явного участия врача.
